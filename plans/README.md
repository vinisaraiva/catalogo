## Dependency notes

- **Plan 001 is not a code plan** — it's a short manual runbook (delete two
  files, rotate three credentials, clear a stale git lock, start
  committing). It has no `npm run` verification gates because it doesn't
  touch application code. Do it before touching anything else: plans 2-6
  all end in a commit, and you don't want live secrets swept into the
  first real commit this project makes.
- **Plan 5 exercises the same tenant boundary that plan 2 fixes**, but
  through a different code path (RLS itself, called directly — not
  through the `createProduct`/`updateProduct` Server Actions plan 2
  patches). They're independent and can be done in either order, but
  doing 2 before 5 means the new test in 5 has company: a second,
  narrower regression test could later be added for the Server-Action-level
  check plan 2 introduces (noted as a maintenance follow-up in plan 2, not
  required by either plan).
- Plans 3, 4, and 6 are fully independent of each other and of 2/5.

## Other findings from this audit not turned into plans

Recorded here so a future run of `/improve` doesn't need to re-discover
them — ask the user before writing plans for any of these:

- Concurrent image uploads can race to the same `sort_order` (no
  transactional reservation of the "next" value) — `src/lib/actions/product-images.ts:82-91`.
- `reorderProductImages` has no rollback if only some of its parallel
  per-row updates fail — `src/lib/actions/product-images.ts:231-241`.
- Zero test coverage on the Server Action / mutation layer generally
  (`src/lib/actions/*.ts`, ~700 lines, no `__tests__`) — large effort,
  needs a Supabase-client mocking strategy this repo doesn't have yet.
- No coverage measurement configured (`vitest.config.ts` has no
  `test.coverage` block) and no CI pipeline (`.github/workflows` doesn't
  exist) — both depend on plan 001's git-hygiene work landing first.
- Duplicated store-ownership-check boilerplate between
  `product-images.ts`'s `isOwnedProduct` and an inline equivalent in
  `product-sizes.ts` — small, cosmetic, no functional risk.
- `src/domain/whatsapp.ts`'s placement diverges from ARCHITECTURE.md §26's
  suggested `lib/whatsapp/` location, undocumented in DECISIONS.md — purely
  organizational.
- `src/domain/slug.ts` has no test file (every sibling domain module does).
- `next`/`eslint-config-next` are one patch release behind
  (`16.3.2` → `16.3.3`) within the already-permitted `^16.3.2` range —
  routine `npm install`, not worth a plan.
- README.md's script table is missing `test:watch`, `format:check`,
  `db:reset`.
- DECISIONS.md jumps from ADR-024 straight to "Open validation items" —
  ADR-025/026/027 are cited by five source files (the Phase 5 migration,
  `product.ts` validations, the integration test, etc.) but don't exist in
  the document. Worth fixing, but it's a documentation-only change with no
  code/behavior impact, so it wasn't prioritized into a plan — happy to
  write one if wanted.
- No E2E test framework exists at all (expected at this project stage per
  CLAUDE.md's own testing roadmap — Phase 8 scope).
